# 短链接系统设计思路（阶段1）

> 项目：短链接服务　阶段：阶段1 核心链路　包名：com.bq.shortlink　端口：8080

## 1. 项目定位与范围

一句话：把长链接转换成短码，访问短码 302 跳转到原链接，并提供短链接详情查询。

阶段1 的目标是在本地 MySQL + Spring Boot 环境下跑通"创建、存储、跳转、查询"闭环，代码分层清晰、异常统一、表结构可扩展，为阶段2-4 的缓存、统计、限流留好位置。

| 能力 | 阶段1 | 说明 |
| --- | --- | --- |
| 创建短链接 | 支持 | 长链接转短码，可选过期天数 |
| 302 跳转 | 支持 | 访问短码临时重定向到长链接 |
| 查询详情 | 支持 | 返回短码、短链、长链、访问次数、创建与过期时间 |
| 测试页 | 支持 | GET / 极简蓝白测试页 |
| 幂等创建 | 支持 | 同一 long_url 再次创建直接返回已有短码 |
| 过期控制 | 支持 | expire_time 为空表示永不过期 |
| Redis 缓存 | 不启用 | 依赖已引入，自动配置关闭，阶段2 启用 |
| 访问统计、限流、用户体系 | 不做 | 阶段3-4 |

## 2. 技术选型与不引入项

| 组件 | 版本 | 选型理由 |
| --- | --- | --- |
| Spring Boot | 3.5.11 | 内嵌 Tomcat、自动配置，单模块快速起步 |
| Java | 21 | LTS 版本，长期维护 |
| MyBatis-Plus | 3.5.15 | 单表 CRUD 与条件构造器，减少样板代码，便于后续分页与逻辑删除 |
| MySQL | 8.0.43 | 本地 shortlink 库，InnoDB 事务与唯一索引保证短码唯一 |
| Redis | 依赖已引入 | 阶段1 不启用，阶段2 做缓存与计数；通过排除自动配置避免启动时连接 Redis |

不引入项及理由：

- 不启用 Redis：阶段1 数据量与并发都很小，直连 MySQL 足够；提前接入只会增加缓存一致性负担。
- 不引入 MQ、分布式锁、微服务：单体应用即可覆盖，避免过度设计。
- 不引入 Swagger、Knife4j：接口只有 3 个，本文档与《接口文档.md》就是契约。
- 不引入 Spring Security：阶段1 没有登录、权限与用户体系。
- 不引入前端工程：测试页就是一个静态 HTML 文件，不引入构建工具。

## 3. 数据库设计

### 3.1 表结构

建库建表脚本位于 `sql/init.sql`（数据库 shortlink，字符集 utf8mb4）。

```sql
CREATE TABLE t_short_link (
    id          BIGINT        NOT NULL COMMENT '雪花ID',
    short_code  VARCHAR(10)   NOT NULL COMMENT '短码',
    long_url    VARCHAR(2048) NOT NULL COMMENT '长链接',
    user_id     BIGINT                 COMMENT '创建人',
    visit_count BIGINT        NOT NULL DEFAULT 0 COMMENT '访问次数',
    create_time DATETIME      DEFAULT CURRENT_TIMESTAMP,
    expire_time DATETIME               COMMENT '过期时间，NULL永不过期',
    PRIMARY KEY (id),
    UNIQUE KEY uk_short_code (short_code),
    KEY idx_user (user_id),
    KEY idx_long_url (long_url(191))
) ENGINE = InnoDB COMMENT = '短链接表';
```

### 3.2 字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 雪花算法生成的主键，同时是短码的数值来源 |
| short_code | VARCHAR(10) | 62 进制短码，唯一索引 |
| long_url | VARCHAR(2048) | 原始长链接，浏览器地址栏的实际上限通常远小于此 |
| user_id | BIGINT | 预留，阶段1 不写入、不查询 |
| visit_count | BIGINT | 冗余访问次数，阶段1 固定写入 0，阶段3 接入统计后跳转时自增 |
| create_time | DATETIME | 创建时间，应用写入；数据库默认值 CURRENT_TIMESTAMP 作为兜底 |
| expire_time | DATETIME | 过期时间，NULL 表示永不过期 |

### 3.3 索引设计

| 索引名 | 类型 | 字段 | 用途 |
| --- | --- | --- | --- |
| PRIMARY | 主键 | id | 聚簇索引，按时间趋势顺序写入 |
| uk_short_code | 唯一 | short_code | 跳转与详情按短码等值查询，并兜底短码唯一 |
| idx_user | 普通 | user_id | 预留按用户查列表，阶段1 不启用 |
| idx_long_url | 普通前缀 | long_url(191) | 幂等查询 WHERE long_url = ? |

### 3.4 关键取舍

**为什么用雪花 ID，而不是自增 ID 或 UUID**

- 自增 ID 会暴露业务量、可被遍历，且短码由 ID 映射后可以被顺序猜测；雪花 ID 含时间戳，同样趋势递增（利于 InnoDB 聚簇索引顺序插入，减少页分裂），但需要额外信息才能还原规律。
- UUID 无序，作为主键写入会随机插入导致页分裂与索引膨胀，字符串形式也更占空间。
- 雪花 ID 本地生成，不依赖数据库号段表或中心服务，单机即可产出全局唯一 ID；而随机生成短码需要每次查询数据库判重并重试。
- 短码由雪花 ID 直接编码，天然唯一，跳转查询只走唯一索引，无需额外的"短码→ID"映射表。

**为什么冗余 visit_count，而不是单独建访问流水表**

- 建表阶段就把访问次数作为主表字段预留，详情接口可以直接返回，避免后续加字段与迁移。
- 阶段1 不统计访问（访问统计属于阶段3），跳转链路只读不写，`visit_count` 固定为 0；阶段3 再在跳转时执行 `UPDATE t_short_link SET visit_count = visit_count + 1 WHERE short_code = ?`，数据库行锁保证并发自增不丢数，不需要应用层加锁。
- 局限：热点链接会频繁更新同一行，且没有明细可查。阶段3 引入访问日志表与统计任务后，visit_count 保留为"当前累计值"，明细由日志表承担。
- 阶段2 接入 Redis 后，可改为 Redis 计数 + 定时回写数据库，降低主库压力。

**为什么 long_url 用前 191 位前缀索引**

- long_url 是 VARCHAR(2048)，若建完整索引会超出索引长度限制并浪费空间。
- 前缀索引只存储前 191 个字符，足以区分绝大多数 URL；191 是 utf8mb4 下兼容旧版 767 字节行格式的经典取值（767 / 4 = 191）。
- 前缀索引只存前缀，MySQL 命中后需要回表读取完整 long_url 再比对，因此等值查询依旧正确，只是多一次回表；这在幂等查询这种低频操作上完全可接受。
- 注意：前缀索引不能用于覆盖索引优化，也不支持对 long_url 做排序；阶段1 都不需要。

**short_code 的大小写敏感性**

62 进制字符集包含 a-z 与 A-Z，两者编码值不同，因此短码本身区分大小写。当前表使用 MySQL 默认的 utf8mb4_general_ci 排序规则（不区分大小写），理论上不同 ID 编码出"仅大小写不同"的短码时会被唯一索引误判冲突，概率极低，阶段1 可接受。若需要严格保证，可把该列改为 `ascii_bin` 排序规则。

## 5. 核心流程

### 5.1 创建短链接

1. 接收 `POST /api/shortlink/create`，校验 longUrl 非空（为空返回 50001）且以 http:// 或 https:// 开头（格式不合法返回 50002；白名单协议，避免 javascript:、file: 等危险协议）；长度上限 2048 由字段约束，超长写入会失败并由兜底异常返回 50000。
2. 处理过期时间：expireDays 为空、为 null 或小于等于 0 时 expire_time 为 NULL；否则 expire_time = 当前时间 + expireDays 天。
3. 幂等查询：按 long_url 查最新一条记录（ORDER BY id DESC LIMIT 1），若存在且未过期则直接返回已有短码；已过期记录不作为幂等命中，否则会立即返回一个跳转 404 的短码，因此按新链接重新生成。
4. 生成 ID 与短码：`id = snowflakeUtil.nextId()`，`short_code = shortCodeUtil.encode(id)`。
5. 落库：写入 id、short_code、long_url、visit_count=0、create_time、expire_time。
6. 组装返回：shortUrl = 配置项 shortlink.domain（默认 `http://localhost:8080/`）+ shortCode，返回 ShortLinkVO。

幂等边界说明：阶段1 的幂等是"先查后插"，并发同时创建同一 long_url 时仍可能产生两条不同短码的记录（idx_long_url 不是唯一索引，无法用数据库约束兜底）。量小场景可接受；若要求强幂等，可对 long_url 计算 64 位哈希后加唯一索引，或加分布式锁（阶段2+）。

### 5.2 短码跳转

1. 接收 `GET /{shortCode}`（正则 `[0-9a-zA-Z]+`），按短码查询记录。
2. 记录不存在，返回 HTTP 404（无响应体）。
3. 记录存在且 expire_time 不为空且已早于当前时间，同样返回 HTTP 404（无响应体；过期不跳转，也不暴露原链接）。
4. 校验通过后直接返回 HTTP 302，Location 为 long_url。阶段1 不做访问统计（阶段3 再在此处原子自增 visit_count，或累加到 Redis 后异步回写）。

跳转使用 302 而不是 301：301 会被浏览器长期缓存，后续修改目标地址或做访问统计都会失真；302 每次都会回到服务端，保留控制权。

### 5.3 查询详情

按 short_code 查询，不存在返回业务错误码 50003（HTTP 200）；存在则返回 ShortLinkVO（含 visitCount、createTime、expireTime），阶段1 visitCount 固定为 0。已过期的短码仍可查到详情，便于页面展示与排查，但跳转接口会拦截，两者行为不同。

## 6. 雪花算法详解

### 6.1 位结构

| 位数 | 含义 | 说明 |
| --- | --- | --- |
| 1 bit | 符号位 | 固定为 0，保证 ID 为正数 |
| 41 bit | 毫秒时间戳 | 相对自定义纪元 2024-01-01 00:00:00（UTC+8）的偏移量，可用约 69.7 年 |
| 10 bit | 机器 ID | 从配置 shortlink.worker-id 读取（默认 1），最多 1024 个节点 |
| 12 bit | 序列号 | 同一毫秒同一节点最多生成 4096 个 ID |

单节点理论峰值约 4096 个 ID/毫秒，即约 409.6 万个/秒，远超阶段1 需求。

### 6.2 生成逻辑

- 方法整体 synchronized，保证同一时刻只有一个线程发号。
- 取当前毫秒时间戳，若小于上一次时间戳，说明发生了时钟回拨，直接抛异常拒绝发号。
- 若等于上一次时间戳，序列号 +1；序列号溢出（超过 4095）则自旋等待下一毫秒。
- 若大于上一次时间戳，序列号归零，更新 lastTimestamp。
- 最后按位拼接：`((timestamp - EPOCH) << 22) | (workerId << 12) | sequence`。

### 6.3 时钟回拨风险

服务器 NTP 校时、手动改时间都可能导致时间回拨，从而生成重复 ID。阶段1 采用简单策略：检测到当前时间小于 lastTimestamp 时直接抛出异常拒绝发号，让创建请求失败并暴露问题，避免产生重复短码。代价是回拨期间服务不可用；后续可优化为小幅回拨自旋等待、大幅回拨告警并切换 workerId。生产环境还应保证同一集群内 workerId 不重复（配置项 shortlink.worker-id 或环境变量 SHORTLINK_WORKER_ID）。

### 6.4 短码长度与字段容量

雪花 ID 是 63 位整数，起始纪元为 2024-01-01，当前（2026 年）转 62 进制为 10 位，例如 `1aB3dK9xYz` 这种 9-10 位字母数字组合。short_code 字段定义为 VARCHAR(10)，可容纳的最大值为 62^10 ≈ 8.39×10^17，按当前发号速度大约能用到 2030 年，之后需要扩宽字段或改用独立发号器。62^6 ≈ 568 亿只作为"6 位短码容量"的参考，说明 62 进制空间足够大，阶段1 并不把短码压到 6 位；若未来产品强要求 6 位定长短码，再引入独立发号器（号段模式或 Redis INCR）即可。

## 7. 62 进制编码与容量

字符表按 `0-9a-zA-Z` 排列，共 62 个字符，与短码正则 `[0-9a-zA-Z]+` 对应。编码规则：ID 反复对 62 取余，余数查表得到字符，再整除 62，直到商为 0，最后反转字符串。解码是逆过程，可用于排查与测试。

容量对照：

| 位数 | 容量 | 说明 |
| --- | --- | --- |
| 6 位 | 62^6 ≈ 568 亿 | 6 位短码的容量上限，作为容量参考 |
| 7 位 | 62^7 ≈ 3.52 万亿 | |
| 10 位 | 62^10 ≈ 8.39×10^17 | 覆盖当前雪花 ID 数量级（约 3.8×10^17） |

阶段1 不补前导零：ID 较小时短码较短，随着时间推移逐渐变长，当前稳定在 10 位，VARCHAR(10) 可容纳到 62^10 ≈ 8.39×10^17（约 2030 年），届时需要扩宽字段或改用独立发号器。若要求定长，可在左侧补 0，但会浪费编码空间，阶段1 不采用。

## 8. 路径冲突处理

RedirectController 使用 `@GetMapping("/{shortCode:[0-9a-zA-Z]+}")` 做单段路径匹配，天然规避冲突：

- `/`（根路径）为空串，不匹配，交给静态资源欢迎页 index.html。
- `/index.html`、`/favicon.ico` 含点号，不匹配，交给静态资源处理器。
- `/api/shortlink/create` 等多段路径含斜杠，不匹配，只命中 ShortLinkController。
- `/error` 虽然字面上是合法短码，但它只在错误转发时出现，即使被匹配到也只会查询不到并返回 404，不会造成循环跳转；若未来引入 actuator，需要把其路径加入排除规则。

短码查询统一走唯一索引等值匹配，不存在模糊查询或路径变量歧义。

## 9. 异常与统一返回

统一返回结构 `Result{code, msg, data}`。成功时 code=200、msg 为"成功"；失败时 msg 为可读提示。业务码约定如下：

| code | 含义 | 触发场景 |
| --- | --- | --- |
| 200 | 成功 | 创建、查询成功 |
| 50000 | 系统异常 | 未捕获异常、数据库错误等 |
| 50001 | 长链接为空 | longUrl 为 null、空串或全空白 |
| 50002 | 长链接格式错误 | 不是 http:// 或 https:// 开头 |
| 50003 | 短链接不存在 | 详情查询的 shortCode 查不到记录 |

异常处理：

- 业务可预期错误抛 `BizException(code, msg)`，由 `GlobalExceptionHandler` 捕获并转换为 Result，避免在 Service 里层层判断返回值。
- 未捕获异常统一按 50000 处理，记录 error 日志，不把堆栈返回给前端。
- `/api/**` 的 HTTP 状态始终为 200，业务结果只由 Result.code 表达；不使用 HTTP 400/404/500 表达业务错误，避免调用方两套判断逻辑。
- 跳转接口不返回 JSON：短码不存在或已过期返回真实 HTTP 404 且无响应体，成功返回真实 HTTP 302 与 Location，与浏览器行为保持一致。
- 静态测试页 `GET /` 返回 HTTP 200 + HTML。

## 10. 配置与 profile

配置分三层，避免密码进入仓库：

- `application.yml`（提交）：公共配置。server.port=${SERVER_PORT:8080}、应用名、默认激活 local profile（`${SPRING_PROFILES_ACTIVE:local}`）、数据源 url（不含密码）、排除 Redis 自动配置（RedisAutoConfiguration 与 RedisRepositoriesAutoConfiguration）、MyBatis-Plus 的驼峰映射与 id-type=input、业务配置 shortlink.domain 与 shortlink.worker-id。
- `application-local.yml`（本地，加入 .gitignore，不提交）：本地数据源账号密码、连接池参数，以及阶段2 才用到的 Redis 连接信息，仅供本机使用。
- `application-local.yml.example`（提交）：模板文件，密码写成占位符，新成员复制为 application-local.yml 后填写自己的密码。

要点：

- 文档、代码、提交记录中都不出现密码明文；数据库账号密码只存在于本地被忽略的文件。
- 阶段1 关闭 Redis 自动配置，因此即使本机没启动 Redis 也能正常启动项目；阶段2 去掉 exclude 并补充 Redis 连接配置即可。
- 可用 `--spring.profiles.active=local`、环境变量 SPRING_PROFILES_ACTIVE、SERVER_PORT、SHORTLINK_DOMAIN、SHORTLINK_WORKER_ID 覆盖默认值，便于后续部署到测试环境。

## 11. 阶段1 边界与后续规划

阶段1 明确不做：Redis 缓存、访问明细统计、限流防刷、用户登录与权限、自定义短码、管理后台、分布式部署。

后续阶段：

- 阶段2 缓存：短码到长链接的 cache-aside 缓存，配合空值缓存、布隆过滤器、逻辑过期或互斥锁处理穿透、击穿、雪崩；访问次数改 Redis 累加，定时回写 MySQL。
- 阶段3 统计：访问日志表记录 PV、UV、来源、UA、地区等，离线或定时聚合；详情页展示趋势。
- 阶段4 限流与治理：按 IP/用户维度令牌桶或滑动窗口限流，黑白名单，链接禁用与举报，监控告警。
- 可选优化：6 位定长短码发号器、long_url 哈希唯一索引实现强幂等、分库分表与号段模式。

## 12. 面试点小结

- 为什么用雪花 ID：趋势递增、本地生成、不暴露自增规律，避免 UUID 随机写放大。
- 短码如何保证唯一：雪花 ID 本身唯一，62 进制编码只是一一映射，再由唯一索引兜底。
- 幂等怎么做：按 long_url 查询复用；并发场景的不足与哈希唯一索引方案。
- 为什么 302 不是 301：保留服务端控制权，便于统计与改链。
- 为什么前缀索引 191：utf8mb4 与索引长度限制，回表比对完整值。
- 缓存三兄弟：穿透（空值缓存、布隆过滤器）、击穿（互斥重建、逻辑过期）、雪崩（过期时间打散、多级缓存）。
- 时钟回拨如何处理：阶段1 检测到回拨直接拒绝发号，可扩展为小幅自旋等待、大幅告警。
- 62 进制容量：62^6≈568 亿，位数与容量的指数关系。
- 热点行更新：visit_count 单行自增的瓶颈，以及 Redis 计数 + 异步回写的演进方向。
